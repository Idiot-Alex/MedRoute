# 多楼层导航实施方案

## 1. 目的与适用范围

本文是 MedRoute 后续实施的基准方案，用于把单层 Demo 演进为可维护的多楼层医院室内路线引导系统。

系统面向少量地图维护人员和大量只读导航用户。第一阶段不做实时定位、微服务、消息队列、Redis、PostGIS 或复杂 GIS 平台；优先保证建图、发布、跨层路线和临时封闭状态可靠可用。

## 2. 当前基线

当前仓库已经具备：

- 单层 SVG 路线导航 Demo 和基础图编辑器。
- Spring Boot API、PostgreSQL 三层发布图和普通/无障碍跨层路线。
- 显式的 POI、楼层、路径节点、路径边、垂直设施、停靠点和跨层边模型。
- 以时间为主成本、距离为次级排序的 Dijkstra，以及分楼层路线响应。
- `expectedReleaseId` 一致性校验、持久化临时封闭、标准错误响应和请求 ID。
- 每层底图上传、路网编修、草稿校验、发布、回滚和草稿删除后台。
- 基于后端路线结果的多楼层导航页面和真实公开底图测试资产。

当前生产化仍需补齐：

- 正式登录、管理员角色和医院/楼栋数据权限。
- HTTPS、反向代理、受控 CORS、监控告警和自动备份。
- 经医院授权的真实底图、完整 POI 数据和现场路线复核。
- 路线反馈、错误上报和多医院数据管理。

## 3. 实施原则

### 3.1 以楼栋导航图为发布单位

每层地图可以独立编辑，但跨楼层路线必须使用同一组已发布数据。系统以 `building_map_release` 为路线计算单位，而不是单独的楼层地图版本。

一份发布版本固定包含：

- 每层采用的楼层图片修订版。
- 每层的 POI、路径节点和楼层内路径边。
- 电梯、楼梯、扶梯等跨层设施和连接边。
- 发布状态、发布时间和发布人。

编辑只发生在草稿版本；导航服务只读取已发布版本。一栋楼在同一时刻只能有一个启用版本。

### 3.2 路线图与临时运营状态分离

施工封路、电梯停运、夜间关闭等不应修改已发布地图。此类信息保存为有效期明确的覆盖规则，并在计算路线时叠加到已发布图上。

这样可以即时生效、定时失效、保留原因和操作记录，也不会因一次临时封闭重新发布整栋楼。

### 3.3 以预计通行成本规划路线

路线成本以 `time_seconds` 为主，距离只用于展示和辅助校验。路径边必须显式记录方向、类型、无障碍能力、状态和备注。

第一版使用 Dijkstra。不同楼层图片没有统一坐标系，不能用图片像素距离作为 A* 启发函数。图规模较小时，Dijkstra 更容易验证正确性。

### 3.4 保持模块化单体

第一版部署一个 Spring Boot 服务即可。按代码包和领域接口隔离模块，避免提前拆微服务：

```text
map-catalog      医院、院区、楼栋、楼层和图片修订版
map-authoring    草稿编辑、校验、发布和回滚
navigation       图装配、路线计算、分楼层路径和文字指引
operations       临时封闭、开放时段和运营备注
admin-api        维护端接口
navigation-api   用户导航接口
```

## 4. 目标架构

```text
维护端地图编辑器
        |
        v
Spring Boot: map-authoring ----> PostgreSQL
        |                           |
        |                           +--> Flyway 迁移记录
        v
已发布楼栋导航图 <---- 临时运营状态
        |
        v
Spring Boot: navigation
        |
        +--> 路线响应（按楼层分段、跨层动作、文字步骤）
        |
        v
H5 / 小程序 / App WebView
```

当前轻量单实例版本将底图二进制保存在 PostgreSQL 的独立资产表中，并通过不可变
图片接口读取，使地图、版本和底图可以一次备份。未来底图规模或访问量明显增加时，
可保持修订版元数据和 URL 契约不变，将资产内容迁移到对象存储。

## 5. 核心数据模型

### 5.1 组织与地图层级

```text
Hospital
  Campus
    Building
      Floor
        FloorMapRevision

BuildingMapRelease
  -> 选用一个或多个 FloorMapRevision
  -> 包含该楼栋完整导航图快照
```

`Campus` 必须正式入库，不再只停留在文档层级。`Floor` 保留标准楼层编码，例如 `B1`、`1F`、`2F`，并以 `level_no` 表示排序。

### 5.2 图元素

| 实体 | 作用 | 关键字段 |
|---|---|---|
| `path_node` | 路线图节点 | `release_id`、`floor_id`、`code`、`x`、`y`、`node_type` |
| `path_edge` | 楼层内或普通通行边 | `release_id`、`code`、`from_node_id`、`to_node_id`、`time_seconds`、`distance_meters`、`direction`、`edge_type`、`accessible` |
| `poi` | 可搜索的目的地 | `release_id`、`floor_id`、`code`、`node_id`、`name`、`category`、`keywords` |
| `vertical_connector` | 电梯、楼梯、扶梯等设施本体 | `release_id`、`code`、`name`、`connector_type`、`accessible` |
| `connector_stop` | 设施在某楼层的落点 | `connector_id`、`floor_id`、`node_id`、`stop_code` |
| `vertical_link` | 两个落点间实际可走的跨层边 | `release_id`、`code`、`from_stop_id`、`to_stop_id`、`time_seconds`、`direction`、`accessible` |
| `edge_state_override` | 临时运营覆盖 | `building_id`、`edge_code`、`status`、`effective_from`、`effective_to`、`reason` |

`vertical_connector` 只表示设施身份；是否能从某层到另一层由 `vertical_link` 明确决定。不能仅凭相同电梯编号假设它经过全部楼层。

### 5.3 ID 与业务编码

- 数据库使用不可变主键作为内部关联键。
- `N1`、`P1`、`ELEV-A` 等仅作为人可读业务编码，且在对应发布版本内唯一。
- API 对外返回稳定的公开 ID 或业务编码，不将数据库自增 ID 作为长期客户端契约。
- 路线、反馈和运营覆盖都要记录 `release_id`，保证历史记录可重放。

## 6. 路线计算与响应

### 6.1 计算流程

```text
接收 buildingId + expectedReleaseId（可选）+ startPoiId + endPoiId + routeMode
        |
读取楼栋当前发布版本
        |
加载完整楼栋图和生效中的临时覆盖规则
        |
按 routeMode 过滤不可通行边
        |
使用 Dijkstra 计算最低通行成本路径
        |
按楼层切分路径，识别跨层连接
        |
生成路线摘要、楼层段、跨层动作和文字步骤
```

普通路线可使用所有符合开放规则的边。无障碍路线必须排除楼梯、不可无障碍通行的边和不可用电梯。员工路线必须由身份权限显式授权，不能仅依赖前端传入一个模式字符串。

### 6.2 路线响应结构节选

路线响应必须包含发布版本和按楼层分段的数据，不能只返回扁平节点列表：
以下只展示关键结构，完整字段和正式示例以 `05-接口设计.md` 第 4.6 节为准。

## 7. API 边界

### 7.1 用户导航 API

- `GET /api/hospitals`：医院列表。
- `GET /api/hospitals/{hospitalId}/buildings`：楼栋列表。
- `GET /api/buildings/{buildingId}/navigation-context`：当前发布版本、楼层元数据和图片地址。
- `GET /api/releases/{releaseId}/floors/{floorId}/graph`：指定楼层的可视化图数据。
- `POST /api/routes`：后端权威路线计算。

`POST /api/routes` 请求必须增加 `buildingId`。路线不能只以 `hospitalId` 为范围，因为同一医院可存在多个楼栋和不同连接关系。

### 7.2 维护端 API

- 草稿版本创建、复制、查询和删除。
- 楼层图片修订版上传与绑定。
- 节点、边、POI、垂直设施、停靠点和跨层边的维护。
- 发布前图校验。
- 发布、回滚和发布记录查询。
- 临时运营状态创建、撤销和有效期查询。

维护端 API 与用户导航 API 分开鉴权。第一版只需要少量管理员角色，但数据模型要预留医院和楼栋范围。

## 8. 分阶段实施

### 阶段 0：契约与设计定稿

**状态：已完成**

**工作内容**

- 更新 `04-数据库设计.md`、`05-接口设计.md`、`06-SpringBoot后端骨架.md`。
- 明确楼栋发布版本、跨层设施、临时覆盖和 API ID 规则。
- 将当前 A* 约束改为 Dijkstra 实施方案。

**完成标准**

- 文档中不存在“单楼层版本即可支撑跨层路线”的冲突描述。
- 所有核心表、API 输入输出和版本归属都有明确说明。

### 阶段 1：多楼层路线核心（内存数据）

**状态：已完成**

**工作内容**

- 为正式路线接口新增 `1F / 2F / 3F` 内存发布图，保留旧单层兼容数据。
- 增加 A 电梯仅停 `1F / 3F`、B 电梯停 `1F / 2F / 3F`、相邻楼层楼梯等场景。
- 用 Dijkstra 替换当前不受校验的图片坐标 A*。
- 组装按楼层分段的路线响应和跨层提示。

**完成标准**

- 普通路线、无障碍路线、封闭电梯、不可达目的地均有自动化测试。
- 系统不会把未停靠的楼层作为电梯可达楼层。
- 所有路线响应均包含 `releaseId`、楼层段和跨层动作。

### 阶段 2：PostgreSQL 与 Flyway 持久化

**状态：已完成**

**工作内容**

- 增加 PostgreSQL 配置、Docker Compose、Maven Wrapper 和环境变量示例。
- 用 Flyway 创建初始迁移和测试数据迁移。
- 实现发布版本查询、图读取和临时覆盖规则读取。
- 以 `JdbcPublishedGraphRepository` 替换正式路线的
  `InMemoryPublishedGraphService`，但保留内存 fixture 作为单元测试数据；
  旧 `DemoGraphService` 随兼容接口另行退役。

**完成标准**

- 空数据库可通过一次启动完成建表和初始化。
- 同一份迁移可在开发、测试和部署环境重复执行。
- 已发布图与草稿图严格隔离，临时状态不改写发布图。

### 阶段 3：最小地图编辑与发布后台

**状态：已完成最小可用版本**

**工作内容**

- 上传/选择楼层图片，按图片像素坐标添加节点、边和 POI。
- 维护电梯、楼梯、扶梯及其各楼层停靠点。
- 发布前执行结构校验，并提供错误说明。
- 支持复制上一发布版本为新草稿、发布和回滚。

**完成标准**

- 维护人员无需修改代码即可完成一栋三层楼的建图和发布。
- 发布校验能识别孤立节点、POI 未绑定节点、跨层连接缺失、无效电梯停靠和重复编码。

### 阶段 4：用户导航页接入后端

**状态：已完成测试版**

**工作内容**

- 前端改为调用 `POST /api/routes`，不再自行计算路线。
- 根据 `segments` 显示对应楼层图片、路径高亮和楼层切换。
- 展示跨层步骤、路线模式和临时封闭提示。
- 用户导航按移动端首屏和触控操作设计，地图维护继续使用独立的桌面工作台。
- 导航 API 请求设置超时，条件变化时取消旧请求，发布版本冲突时刷新数据后只
  重试一次；底图图片加载失败时提供独立重试。

**完成标准**

- 用户看到的路径与后端路线响应一致。
- 从不同楼层的 POI 之间可完成整条路线引导。
- `360 x 800` 和 `390 x 844` 手机视口无页面横向溢出，地图可在首屏查看。

### 阶段 5：运营闭环与多医院

**状态：部分完成**

**工作内容**

- 临时封闭、电梯停运、夜间关闭和运营备注。
- 路线反馈、错误上报、现场复核时间和数据负责人。
- 医院/楼栋数据权限和审计记录。

当前已实现路径、跨层连接和整组设施的定时/立即封闭与撤销，以及发布、回滚事件
记录。路线反馈、多医院权限和完整操作审计留待生产化阶段。

**完成标准**

- 临时状态可在不重新发布地图的情况下影响新路线。
- 维护人员可定位每份发布版本、每次状态变更和每条反馈的归属。

## 9. 发布前质量校验

每次发布至少执行以下自动检查：

- 所有 POI 均绑定有效节点，且节点位于同一楼层。
- 所有边的起点和终点存在，楼层内边不跨楼层。
- 所有垂直连接引用有效停靠点，且停靠点属于同一设施。
- 电梯/扶梯方向配置有效，未配置的楼层不可通行。
- 重要 POI（入口、挂号处、药房、电梯、楼梯）在目标范围内可达。
- 无障碍模式不存在错误经过楼梯的路线。
- 不存在重复的业务编码和无效的图片坐标。

发布后应保留一组固定回归路线，自动验证主要入口到挂号、药房、检验科、影像科和不同楼层目的地均可按预期计算。

## 10. 测试策略

| 层级 | 覆盖重点 |
|---|---|
| 算法单元测试 | 最短成本、单向边、无路可达、边状态、无障碍过滤 |
| 路线服务测试 | 版本选择、临时覆盖、跨层切分、文字步骤 |
| 持久化集成测试 | Flyway 迁移、发布隔离、回滚、查询约束 |
| API 测试 | 参数校验、错误状态、响应契约、权限范围 |
| 前端端到端测试 | 起终点选择、跨层切换、路线高亮、封闭提示 |
| 发布验收测试 | 真实医院抽样路线与现场走查一致 |

## 11. 轻量部署方案

第一版部署只需：

```text
reverse proxy（可选）
Spring Boot 应用
PostgreSQL 数据卷
定时数据库备份
```

当前底图随 PostgreSQL 数据卷保存。未来迁移对象存储时再增加独立图片存储和备份。
仓库提供 `scripts/backup-postgres.sh` 和 `scripts/restore-postgres.sh`，用于生成
带 SHA-256 的 custom format 备份，并默认恢复到独立演练数据库。

不因维护人员少而省略备份、迁移和发布记录。维护人员少意味着不需要复杂的多集群运维，而不是可以忽略数据恢复和版本追溯。

## 12. 第一份可用交付的验收范围

第一份真实可用版本以“一栋三层门诊楼”为范围：

- 1F、2F、3F 各有独立楼层图和可编辑路网。
- 至少一个楼梯、两组停靠范围不同的电梯。
- 从任意入口、挂号处、药房、检验科或影像科可跨层导航。
- 无障碍路线不经过楼梯，并能在电梯停运时给出不可达或替代路线。
- 维护人员可创建草稿、校验、发布、回滚并设置临时封闭。
- 用户端展示后端返回的分楼层路线和跨层指引。

满足以上范围后，再扩展多医院、订单关联、经验备注、路线反馈和可选智能能力。
