# 终端体验与前端实施边界

## 1. 设计结论

导航和地图维护是两类不同任务，不应做成一套折中的通用界面。

| 界面 | 主要终端 | 主要用户 | 交互重点 |
| --- | --- | --- | --- |
| 用户导航 | 手机浏览器 | 患者、家属、陪诊人员 | 单手选择地点、看路线、切换楼层 |
| 地图维护 | 电脑浏览器 | 少量维护人员 | 精确标注、批量检查、版本发布 |

两端共享同一套已发布地图、路线 API 和业务编码，但页面入口、权限和布局独立。
当前对应入口为：

- `hospital-map-demo/multifloor.html`：移动优先的用户导航页。
- `hospital-map-demo/admin.html`：桌面优先的地图维护工作台。

## 2. 移动导航原则

### 2.1 首屏任务

手机首屏按以下顺序组织：

1. 当前楼栋和服务连接状态。
2. 起点、终点和路线偏好。
3. 规划路线按钮。
4. 当前楼层地图。

路线计算后自动定位到地图，地图上方只显示预计时间、距离和第一条跨层动作。
完整文字步骤放在地图之后，避免结果摘要挤占地图空间。

### 2.2 地图查看

- 普通状态显示整层地图，用户先建立整体方位感。
- 点击全屏按钮后使用放大的统一画布，底图与路径覆盖层同步平移。
- 楼层按钮保持至少 `44 x 44 px` 的触控区域。
- 楼层切换只改变当前显示分段，不在浏览器重新计算路线。
- 路线来源始终为当前发布版本的 `POST /api/routes` 响应。

### 2.3 固定点二维码

本项目不做实时定位，推荐在入口、服务台、电梯口和重点科室放置固定点二维码。
二维码 URL 使用楼栋 ID 和稳定的 POI 业务编码，例如：

```text
multifloor.html?building={buildingId}&startPoi={poiCode}
```

手机扫码后自动选择该 POI 为起点。二维码不能保存发布版本内的临时 POI 主键，
否则地图重新发布后可能失效。目的地可由预约通知链接带入，也可由用户搜索选择。

### 2.4 POI 数量扩展

当前测试数据只有少量 POI，原生下拉框足够。接入正式医院数据后，应将起终点选择
替换为移动端搜索面板，至少支持地点名称、科室、楼层、别名和拼音首字母检索。
搜索结果仍提交 POI ID 给路线 API，不改变后端路线契约。

## 3. 桌面维护原则

- 最低验收视口为 `1200 x 720`，推荐使用 `1440 x 900` 或更大屏幕。
- 左侧放版本、楼层和标注工具，中间为可缩放地图，右侧放属性、校验和运营状态。
- 鼠标用于点击、拖动和连边；键盘用于属性录入，不以触屏精确标注为目标。
- 发布版本只读，所有修改在草稿完成校验后一次发布。
- 手机端最多支持紧急查看状态，不承担路网标注和发布验收。

维护端必须调用 `/api/admin` 并接入登录和楼栋权限。导航端只读取发布数据，不应
加载草稿接口或携带维护权限。

## 4. 前端架构边界

当前轻量版本继续使用两个静态页面，不需要拆分后端，也不需要立即开发原生 App。
后续前端工程化时仍建议形成两个独立入口：

```text
navigation-web
  移动优先、匿名只读、发布数据、二维码深链

map-admin-web
  桌面优先、登录鉴权、草稿编辑、校验发布
```

可以共享 API 类型、业务编码和地图坐标转换模块，不共享具体页面布局。这样可以
独立发布导航端高频的小改动，也能避免维护端依赖进入患者手机资源包。

## 5. 验收矩阵

| 场景 | 验收尺寸 | 必查内容 |
| --- | --- | --- |
| 窄屏手机 | `360 x 800` | 无页面横向溢出、地点文本可读、地图进入首屏 |
| 常见手机 | `390 x 844` | 单手完成规划、路线摘要和楼层按钮可触控 |
| 大屏手机 | `430 x 932` | 地图和步骤无异常留白或遮挡 |
| 最低桌面 | `1200 x 720` | 维护三栏可用、中央地图有足够标注空间 |
| 推荐桌面 | `1440 x 900` | 属性、校验、版本操作无需反复切换页面 |

## 6. 后续实施顺序

1. 为正式 POI 增加移动搜索面板和别名、拼音索引。
2. 在维护后台生成固定点二维码，并使用当前已支持的 POI 业务编码深链。
3. 增加路线步骤逐条浏览和前后步骤切换，不引入虚假的实时位置。
4. 为维护后台接入登录、楼栋权限和操作审计。
5. 使用现场手机和维护电脑完成固定路线回归及可读性走查。
