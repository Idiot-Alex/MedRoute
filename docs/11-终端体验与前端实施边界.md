# 终端体验与前端实施边界

## 1. 设计结论

导航和地图维护是两类不同任务，不应做成一套折中的通用界面。

| 界面 | 主要终端 | 主要用户 | 交互重点 |
| --- | --- | --- | --- |
| 用户导航 | 手机浏览器 | 患者、家属、陪诊人员 | 单手选择地点、看路线、切换楼层 |
| 地图维护 | 电脑浏览器 | 少量维护人员 | 精确标注、批量检查、版本发布 |

两端共享同一套已发布地图、路线 API 和业务编码，但页面入口、权限和布局独立。
当前对应入口为：

- `hospital-map-demo/multifloor.html`：移动优先的用户导航页。
- `hospital-map-demo/admin.html`：桌面优先的地图维护工作台。
- `frontend/apps/navigation-web`：Vue/OpenLayers 新导航端。
- `frontend/apps/map-admin-web`：Vue/OpenLayers 新维护端。

## 2. 移动导航原则

### 2.1 首屏任务

手机首屏按以下顺序组织：

1. 当前楼栋和服务连接状态。
2. 起点、终点和路线偏好。
3. 规划路线按钮。
4. 当前楼层地图。

路线计算后自动定位到地图，地图上方只显示预计时间、距离和第一条跨层动作。
完整文字步骤放在地图之后，避免结果摘要挤占地图空间。

### 2.2 地图查看

- 普通状态显示整层地图，用户先建立整体方位感。
- 点击全屏按钮后使用放大的统一画布，底图与路径覆盖层同步平移。
- 楼层按钮保持至少 `44 x 44 px` 的触控区域。
- 楼层切换只改变当前显示分段，不在浏览器重新计算路线。
- 路线来源始终为当前发布版本的 `POST /api/routes` 响应。

### 2.3 固定点二维码

本项目不做实时定位，推荐在入口、服务台、电梯口和重点科室放置固定点二维码。
二维码 URL 使用楼栋 ID 和稳定的 POI 业务编码，例如：

```text
multifloor.html?building={buildingId}&startPoi={poiCode}
```

手机扫码后自动选择该 POI 为起点。二维码不能保存发布版本内的临时 POI 主键，
否则地图重新发布后可能失效。目的地可由预约通知链接带入，也可由用户搜索选择。

### 2.4 POI 搜索

移动导航页使用底部搜索面板选择起点和终点，支持地点名称、POI 编码、分类、楼层、
中文别名、完整拼音和拼音首字母检索，并可按楼层筛选。拼音不由浏览器猜测，统一
维护在 POI 搜索关键词中，避免多音字或医院内部简称产生错误结果。

搜索面板读取当前发布版本的完整 POI 列表，本地过滤后仍提交 POI ID 给路线 API，
不改变后端路线契约。用户选择地点或互换起终点后，页面 URL 同步保存稳定业务编码，
刷新页面不会依赖发布版本内的临时主键。

### 2.5 逐条路线说明

路线计算完成后，用户可从地图摘要打开逐条步骤面板。面板支持上一步、下一步和
完成操作，当前步骤变化时同步切换对应楼层底图；“查看此楼层地图”会保留步骤
进度并收起面板。

步骤只能由用户手动推进，不使用倒计时或模拟移动自动推进。界面明确标记为
“固定路线说明”，当前步骤表示用户正在查看的说明，不表示系统检测到的实时位置。
完整步骤列表继续保留在地图之后，便于一次性核对整条路线。

## 3. 桌面维护原则

- 最低验收视口为 `1200 x 720`，推荐使用 `1440 x 900` 或更大屏幕。
- 左侧放版本、楼层和标注工具，中间为可缩放地图，右侧放属性、校验和运营状态。
- 鼠标用于点击、拖动和连边；键盘用于属性录入，不以触屏精确标注为目标。
- 发布版本只读，所有修改在草稿完成校验后一次发布。
- 手机端最多支持紧急查看状态，不承担路网标注和发布验收。

维护端必须调用 `/api/admin` 并接入登录和楼栋权限。导航端只读取发布数据，不应
加载草稿接口或携带维护权限。

## 4. 前端架构边界

静态页面继续作为稳定验收基线，新版前端已经形成两个独立应用：

```text
frontend/apps/navigation-web
  移动优先、匿名只读、发布数据

frontend/apps/map-admin-web
  桌面优先、草稿编辑；登录鉴权后置

frontend/packages/api-client
  维护端和导航端 API 客户端

frontend/packages/map-core
  领域类型、图数据操作、像素坐标转换和 OpenLayers 图层
```

两端共享 API 类型、业务编码和地图坐标转换模块，不共享具体页面布局。这样可以
独立发布导航端高频的小改动，也能避免维护端依赖进入患者手机资源包。

当前新版前端已完成底图和路网渲染、节点/路径/POI/跨层设施维护、草稿保存、
底图替换、关键路线回归、校验发布、历史版本回滚，以及移动端完整 POI 搜索、
稳定编码深链、路线计算和逐步导航。新版维护端也已接入当前发布版本的运营封闭
与固定点二维码，并补齐普通图元素全部后端字段、同层引用重绑、搜索词维护、
依赖定位和安全删除。静态页面继续作为兼容验收基线，当前尚待真实后端文件上传
和完整业务闭环验收。

## 5. 验收矩阵

| 场景 | 验收尺寸 | 必查内容 |
| --- | --- | --- |
| 窄屏手机 | `360 x 800` | 无页面横向溢出、地点文本可读、地图进入首屏 |
| 常见手机 | `390 x 844` | 单手完成规划、路线摘要和楼层按钮可触控 |
| 大屏手机 | `430 x 932` | 地图和步骤无异常留白或遮挡 |
| 最低桌面 | `1200 x 720` | 维护三栏可用、中央地图有足够标注空间 |
| 推荐桌面 | `1440 x 900` | 属性、校验、版本操作无需反复切换页面 |

## 6. 后续实施顺序

已完成：

1. 移动端 POI 搜索、楼层筛选、别名和拼音关键词检索。
2. 稳定 POI 业务编码深链、兼容旧参数和失效地点回退提示。
3. 路线步骤逐条浏览、前后切换和楼层地图联动。
4. 楼栋关键路线配置、草稿自动回归和关键失败发布阻断。
5. 跨层设施编辑、底图替换、校验发布和历史版本回滚。
6. 静态维护页固定点二维码生成、地址复制和 PNG 下载。
7. 三层公开底图试点草稿、30 个 POI 和 12 条关键路线的自动验收。
8. 新版维护端运营封闭、地图对象定位、恢复和状态刷新。
9. 新版维护端当前发布 POI 选择、二维码地址复制和 PNG 下载。
10. 新版维护端节点、路径和 POI 完整属性、引用重绑、依赖定位和安全删除。
11. 真实 PostgreSQL 当前发布版本的 29 条普通/无障碍路线矩阵、二维码和可逆
    运营封闭 API 回归。

下一阶段：

1. 用真实文件复核底图上传、坐标缩放、草稿保存/放弃和发布/回滚。
2. 由医院人员使用现场手机和维护电脑执行关键路线及可读性走查。
3. 用宿主 App WebView 验证扫码深链、返回行为和弱网提示。
4. 功能稳定后再通过可替换 `AuthAdapter` 接入宿主项目的登录和楼栋权限。
